## 记录

### 2026-11-01 · M0 · AI 记忆里的“最新版本”早就过时了

- **现象**：AI 写的初稿里，CI 用的是 `actions/checkout@v4`、`astral-sh/setup-uv@v6`、`gitleaks/gitleaks-action@v2`；设计 M1 时默认 DeepSeek 的模型叫 `deepseek-chat` / `deepseek-reasoner`；以为 Starlette 的 `TestClient` 依赖 `httpx`。
- **怎么发现的**：
  - 用 `gh api repos/<owner>/<repo>/releases/latest` 查到实际最新版本是 checkout v7、setup-uv v10、gitleaks-action v3；
  - 让一个子 agent 去读 DeepSeek 官方文档，发现旧模型名已于 2026-07-24 下线，新模型是 `deepseek-flash` / `deepseek-v4-pro`，而且**思考模式默认开启**；
  - 测试输出里出现 `StarletteDeprecationWarning`，提示改用 `httpx2`。
- **根因**：模型的训练数据有截止日期，它“记得”的版本号和 API 细节会落后于现实，而且它不会主动意识到这一点。
- **怎么修的**：CI 升级到当前版本；M1 改用 `deepseek-flash`，并且每次请求都显式关闭思考模式；开发依赖换成 `httpx2`。
- **以后怎么防**：CLAUDE.md 加了一条规则：第三方版本和外部 API 的细节必须先查当前文档或最新 release，不能凭记忆；能用一次真实调用验证的（比如列出模型），就去验证。

### 2026-11-01 · M0 · CI 第一次运行，两项检查都失败

- **现象**：PR #1 的 `python` 和 `secrets` 两个任务都失败了。
  1. `python`：`Unable to resolve action astral-sh/setup-uv@v10`。上一条记录里 AI 查到了最新版本是 v10.3.3，就想当然地写成 `@v10`，但这个仓库从 v8 起只发布完整版本号的标签，**没有 `v10` 这种浮动的大版本标签**。
  2. `secrets`：gitleaks 在两个 README 里发现了 `curl -H "Authorization: Bearer dev-mock-pay-key"`，按“curl 请求头里的令牌”规则报警。
- **怎么发现的**：CI 日志（`gh run view --log-failed`）。
- **根因**：
  1. 查证只做了一半：查了“最新版本是多少”，没查“这个标签是否存在”，套用了其他 action 的惯例。
  2. 这个值是文档里公开的本地开发 key，不是真密钥；扫描器是按格式判断的，它报警是正常行为。
- **怎么修的**：
  1. 所有第三方 action 改为**固定到 commit SHA**，并在注释里写明版本（`@<sha> # v10.3.0`）。标签可以被改指向，SHA 不能，这也是防供应链攻击的通行做法。版本只选发布满两周的。
  2. 新增 `.gitleaks.toml`，在默认规则的基础上只放行 `dev-mock-pay-key` 这一个精确值；工作流里显式指定配置文件路径和 gitleaks 版本，不依赖 action 内置的默认版本。
- **以后怎么防**：引用 action 一律用 SHA 固定；密钥扫描的例外只能是精确值，并在配置里写明原因。

### 2026-11-01 · M0 · AI 的代码通过了它自己写的 75 个测试，独立审查却找出一条重复打款路径

- **现象**：M0 的 PR 已经 CI 全绿。另起一个子 agent 做独立审查（只给代码，不给我的结论），它找出：
  1. **重试规则的设计漏洞**：重试会覆盖合作方参考号，之后的检查只查最新的那个。如果合作方延迟执行了**最初那次**提交，第三次尝试就会重复打款。另外，超时之后马上查“合作方没有记录”是不可信的，合作方可能几分钟后才执行。
  2. **种子数据自相矛盾**：S02、S10 说“余额不足、等待资金”，但同一时间段里背景数据中同一商户的其他转账照常出款；S06、S07 说“账号无效 / 已销户”，同一个收款人之后又成功收款。顺着钱一查，就能推翻标准答案。
  3. **分页游标**：游标对应的转账不再匹配筛选条件时，接口静默返回空列表，调用方会以为数据取完了。
  4. **测试有漏洞**：有好几个测试即使被测代码出错也照样通过。审查用“变异测试”（故意改坏代码，看测试会不会失败）证明了这一点，比如对空列表的断言恒为真、只检查 `reason_code` 不检查 `eligible`、请求指纹去掉路径后没有任何测试失败。
  5. 小问题：并发读写字典、非 ASCII 的 token 导致 500、照着 `.env.example` 留空的变量会把默认 key 覆盖成空字符串、调用方的自由文本被当作运营人员写的备注存进状态历史。
- **怎么发现的**：独立的审查 agent 读代码，并写脚本复现了每一条（标注“已复现”或“推断”）。
- **根因**：同一个 AI 写的实现和测试有**相同的盲区**：它想到的危险场景，测试里都有；它没想到的，测试里也没有。CI 全绿只说明代码符合 AI 自己的理解。另外，数据生成器只保证了每个场景“自己”成立，没有保证场景和背景数据放在一起仍然一致。
- **怎么修的**：
  1. 转账记录每一次提交（`submissions`），重试规则要求**所有**参考号都查得到、都没有付款记录；增加超时 30 分钟等待期、报价有效期、可用余额三条检查；防重复打款的检查排在前面，保证 `reason_code` 给出最危险的原因。
  2. 新增 `ledger.py` 统一账务规则，余额由账务推导而不是随机生成；缺钱场景按需入金；场景用到的收款人保留给场景；账号无效或被退回只发生在该收款人的最后一笔转账上；新增“往回推账不能为负”“缺钱窗口成立”“坏账号不再收款”等不变量测试。
  3. 游标按它在完整排序里的位置定位，未知游标返回 400；鉴权改为按字节比较；增加兜底的 500 错误处理（同一种错误格式，不泄露内部信息）；空的环境变量回落到默认值；调用方文本单独存进标为不可信的 `audit` 字段。
  4. 补强测试：断言 `eligible`；分页和完整的期望排序逐一比对；同一个 key 用在另一笔转账上必须被拒绝；两个不同 key 并发重试只能成功一次；通过真实存储层复现“早期尝试被延迟执行”。修复过程中我自己又写出了一个永远会通过的测试（断言同时允许 404 和 500），写完回读时发现并改正。
- **以后怎么防**：
  - 涉及资金安全的 PR 必须经过独立审查，审查者只拿到代码，不拿到作者的结论；
  - 能写成不变量的规则都写成不变量测试（比如“往回推账不能为负”），而不是只测几个举例；
  - 对核心规则做变异测试：故意改坏一处，测试必须失败；
  - 一个断言如果对“空结果”也成立，就要再加一条非空断言。

### 2026-11-01 · M0 · AI 生成的种子数据触发了它自己配置的密钥扫描

- **现象**：修完审查意见后推送，PR #1 的 `secrets` 任务失败。gitleaks 的 `generic-api-key` 规则在 `services/mock-pay/src/mock_pay/data/transfers.json` 里报了 60 处，全部是 `request_idempotency_key` 字段。`python` 任务是绿的。
- **怎么发现的**：CI 失败后，上级会话先看到并转告过来；我用 `gh run view --log-failed` 核实，60 处全部是同一条规则、同一个文件、同一个字段，没有真实密钥。
- **根因**：
  - 为了给 S14 留下“没有带幂等键”的证据，AI 给每笔转账加了 `request_idempotency_key`，值是 `ik_` 加 16 位随机十六进制。字段名里有 `key`、值的熵又高，正好命中 gitleaks 的启发式规则。
  - 本地的 `make check` 不跑密钥扫描，所以推送前没发现。这和上一条“查证只做了一半”是同一类问题：改了数据，却没跑完全部检查。
- **怎么修的**：在 `.gitleaks.toml` 里加了一条**三个条件同时满足**才放行的例外：只针对 `generic-api-key` 规则、只限这一个文件、只限 `"request_idempotency_key": "ik_<16 位十六进制>"` 这种行。同一个文件里的其他行和其他规则照常扫描。没有把数据改成“不像密钥”的格式：真实的幂等键往往就是高熵的 UUID，为了躲扫描器把数据改得不真实，不值得。
- **以后怎么防**：新增 `make secrets`，用和 CI 相同的配置在本地扫描（需要先装 gitleaks）；修改种子数据或配置后、推送之前，先跑一遍。
